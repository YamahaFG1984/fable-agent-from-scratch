LLM API 基础

写任何 Agent 代码之前，必须先搞懂怎么和 LLM 对话。这一章的终点是一次真实的"翻车"：裸 LLM 在 GAIA 上答不出需要查资料的题——这个失败正是第 3 章要解决的问题。

2.1两家 API 的共同骨架

OpenAI 和 Anthropic 的调用方式长得不一样，但骨架相同：一个模型名 + 一个 messages 列表 → 一条回复。

openai_call.py
from openai import OpenAI
client = OpenAI()
response = client.chat.completions.create(
    model="gpt-5.4-mini",
    messages=[
        {"role": "system", "content": "You are a helpful assistant."},
        {"role": "user", "content": "What is the capital of France?"}
    ]
)
print(response.choices[0].message.content)

role 只有三种身份：system（开发者设定行为）、user（用户输入）、assistant（模型历史回复）。两家的差异——字段名不同、Anthropic 强制要求 max_tokens——正是下一节要解决的"多厂商割裂"问题。

2.2用 LiteLLM 统一多厂商

litellm_unify.py
from litellm import completion

response = completion(model="gpt-5.4-mini", messages=[...])       # OpenAI
response = completion(model="claude-sonnet-4-6", messages=[...])  # Anthropic

LiteLLM 把所有厂商响应统一成 OpenAI 格式，换模型只需换一个字符串。这是全书的一个关键工程决策：框架的 LLM 通信层（scratch_agents/llm.py 里的 LlmClient）直接构建在 litellm.acompletion 之上，所以第 4 章写好的 Agent 天生支持任何模型厂商。

2.3全章最重要的认知：API 是无状态的

解法就是自己维护一个 messages 列表：每轮把用户输入和模型回复都 append 进去，下次把整个列表重新发过去。这一个模式是全书的种子——第 4 章的 ExecutionContext.events 是它的结构化升级版，第 6 章的记忆系统是"历史太长塞不下时怎么办"的解法。

2.4结构化输出：把 LLM 变成软件组件

structured_output.py
from pydantic import BaseModel

class ExtractedInfo(BaseModel):
    name: str
    email: str
    phone: str | None = None

response = completion(
    model="gpt-5.4-mini",
    messages=[{"role": "user", "content": "..."}],
    response_format=ExtractedInfo,   # ← 关键
)

传入 Pydantic 模型作为 response_format，模型输出就被约束成符合该 schema 的 JSON——程序无法可靠解析自由文本，但能可靠解析 ExtractedInfo。第 4 章 Agent 的 output_type、第 6 章的记忆抽取都靠这一招。

2.5生产三件套：异步、并发限流、自动重试

concurrent_calls.py
semaphore = asyncio.Semaphore(10)   # 最多 10 个请求同时在飞

async def call_llm(prompt: str) -> str:

        response = await acompletion(
            model=..., messages=[...],
            num_retries=3,          # 失败自动指数退避重试
        )
        return ...

results = await asyncio.gather(*tasks, return_exceptions=True)

LLM 调用的瓶颈是网络等待而非本地计算，天然适合异步；Semaphore 防止撞上速率限制；return_exceptions=True 让单个失败不拖垮其余 99 个。这也是为什么框架里 Agent.run() 和所有工具执行全部是 async 的。

2.6实战收尾：裸 LLM 在 GAIA 上的失败

本章用 GAIA 基准把上面所有知识点串起来：让四个模型（gpt-5.5、gpt-5.4-mini、claude-sonnet-4-6、claude-haiku-4-5）在没有任何工具的情况下跑 GAIA。提示词设计里有个值得注意的细节：让模型自己申报 is_solvable（能不能解）。面对"打开这个 Excel 文件统计销量"这类题，裸 LLM 只能诚实地说"我做不到"。

这个失败就是全书的引子

模型缺的不是智力，是"手"。第 3 章给它工具，第 4 章教它自主循环使用工具——从此它才配叫 Agent。

本章要带走的几句话
  1. LLM API = messages 进，一条回复出；role 区分系统 / 用户 / 助手。
  2. API 无状态——记忆是客户端每次重发全部历史造出来的假象，这是理解 Agent 的第一性原理。
  3. LiteLLM 统一多厂商；Pydantic response_format 把 LLM 变成可靠的程序组件。
  4. 生产级调用三件套：异步并发、信号量限流、自动重试。
  5. 裸 LLM 在 GAIA 上的失败证明：它需要工具和执行循环——这正是第 3、4 章要构建的东西。
