第 2 章讲过：LLM 无状态，"记忆"是客户端造出来的假象。本章把这个假象工程化成**三层记忆体系**，解决三个时间尺度的问题：

| 层 | 时间尺度 | 问题 | 解法 |
|----|---------|------|------|
| 执行内上下文 | 一次 run() 内 | 历史太长，塞爆/花钱 | 上下文优化（6.2） |
| 会话 | 多次 run() 之间 | 关掉就忘 | Session（6.3） |
| 长期记忆 | 跨会话/跨任务 | 经验无法积累 | 向量记忆库（6.4） |

## 1. 执行内优化：改视图，不改历史（6.2，Listing 6.1–6.7）

### 新钩子：before_llm_callbacks

第 5 章给了工具前后两个拦截点，本章补上第三个：**LLM 调用前**。签名 `callback(context, request) -> Optional[LlmResponse]`——返回 None 放行（可以就地修改 request），返回 LlmResponse 则直接跳过 LLM 调用（第 4 章埋的可覆写性在这兑现）。

**全章的第一原则（6.2.1）**：优化只动 `LlmRequest.contents`（每次现做的呈现视图），**永不动 `context.events`（存储）**。所以一切优化都是无损的——历史完整保留，可审计、可回放，只是"这次发给模型什么"变了。这正是第 4 章"存储与呈现分离"设计的回报。

### 门槛控制（Listing 6.1）+ 精确计量（Listing 6.4）

```python
def create_optimizer_callback(apply_optimization, threshold=50000):
    async def callback(context, request):
        if count_tokens(request) < threshold:   # 没超标不折腾
            return None
        apply_optimization(context, request)    # 超标才优化
        return None
    return callback
```

```typescript
function createOptimizerCallback(
  applyOptimization: (context: Context, request: LlmRequest) => void,
  threshold: number = 50000
) {
  return async function callback(context: Context, request: LlmRequest): Promise<LlmResponse | null> {
    if (countTokens(request) < threshold) {   // 没超标不折腾
      return null;
    }
    applyOptimization(context, request);      // 超标才优化
    return null;
  };
}
```

`count_tokens` 用 tiktoken 精确计量，三处细节：每条消息 +4 token 固定开销；tool_calls 的函数名和参数也要算；**工具定义本身也占 token**（很多人忘了这块）。

### 策略一：滑动窗口（Listing 6.2）—— 最笨但零成本

保留"到第一条用户消息为止"的头部 + 最近 N 条，中间全扔。注意**用户的原始问题永远保留**——丢了它 Agent 就忘了自己在干嘛。缺点：中间发现的关键信息一起被扔了。

### 策略二：Compaction 压实（Listing 6.5）—— 可恢复的压缩 ⭐

不按位置删，按**内容价值**换：

```python
TOOLRESULT_COMPACTION_RULES = {
    "read_file":  "File content from {file_path}. Re-read if needed.",
    "search_web": "Search results processed. Query: {query}. Re-search if needed.",
}
TOOLCALL_COMPACTION_RULES = {
    "create_file": "[Content saved to file]",   # 写文件的 content 参数也很肥
}
```

```typescript
const TOOLRESULT_COMPACTION_RULES: Record<string, string> = {
  read_file: "File content from {file_path}. Re-read if needed.",
  search_web: "Search results processed. Query: {query}. Re-search if needed.",
};
const TOOLCALL_COMPACTION_RULES: Record<string, string> = {
  create_file: "[Content saved to file]",   // 写文件的 content 参数也很肥
};
```

把肥大的工具结果替换成一句"占位引用"。精妙之处在措辞：**"Re-read if needed"** —— 信息没有消失，文件还在磁盘上、搜索还能再搜，模型需要时可以再调一次工具拿回来。压缩之所以敢做，是因为**操作可重放**。实现上还需要先记下每个 tool_call_id 的参数，才能在压缩 ToolResult 时填出 `{file_path}`、`{query}`。

### 策略三：Summarization 摘要（Listing 6.6）—— 最贵但最智能

把中段历史让 LLM 总结成一段文字，放进 instructions；保留头（用户问题）和尾（最近 keep_recent 条）。

工程难点是**增量摘要**：用 `context.state["last_summary_idx"]` 记住上次摘要到哪了，下次只总结新增部分，避免"重复摘要已摘要的内容"造成信息衰减。

### 组合拳：ContextOptimizer（Listing 6.7）

```python
async def __call__(self, context, request):
    if count_tokens(request) < self.token_threshold: return None   # 1. 量
    apply_compaction(context, request)                             # 2. 先便宜的
    if count_tokens(request) < self.token_threshold: return None   #    够了就停
    await apply_summarization(...)                                 # 3. 不够再上贵的
```

```typescript
async call(context: Context, request: LlmRequest): Promise<LlmResponse | null> {
  if (countTokens(request) < this.tokenThreshold) return null;   // 1. 量
  applyCompaction(context, request);                             // 2. 先便宜的
  if (countTokens(request) < this.tokenThreshold) return null;   //    够了就停
  await applySummarization(/* ... */);                           // 3. 不够再上贵的
  return null;
}
```

分层策略：**便宜的先上，每步之后重新测量，够了就收手。** compaction 是纯字符串替换（零成本），summarization 要额外调一次 LLM（有成本有延迟）。

## 2. Session：跨 run 的会话（6.3.1–6.3.4，Listing 6.8–6.14）

`BaseSessionManager` 抽象出 `create/get/save`（+模板方法 `get_or_create`），`InMemorySessionManager` 是 dict 实现——**接口设计成 async 就是为了换 Redis/Postgres 时不动调用方**。

## 3. Human-in-the-loop 2.0：暂停与恢复（6.3.5–6.3.8，Listing 6.15–6.26）⭐

第 5 章的 `approval_callback` 用 `input()` 同步阻塞——Web 服务里没法用。本章的重做思路：**审批不是"等待"，而是"暂停-持久化-恢复"。**

### 数据结构（Listing 6.15–6.17）

```python
class PendingToolCall(BaseModel):        # Agent → 用户："我想执行这个，批吗？"
    tool_call: ToolCall
    confirmation_message: str

class ToolConfirmation(BaseModel):       # 用户 → Agent："批/不批"
    tool_call_id: str
    approved: bool
    modified_arguments: dict | None      # 还能改参数再批！
    reason: str | None

class AgentResult(BaseModel):
    status: Literal["complete", "pending_confirmation", "error"]
    pending_tool_calls: list[PendingToolCall]
```

```typescript
interface PendingToolCall {               // Agent → 用户："我想执行这个，批吗？"
  toolCall: ToolCall;
  confirmationMessage: string;
}

interface ToolConfirmation {              // 用户 → Agent："批/不批"
  toolCallId: string;
  approved: boolean;
  modifiedArguments: Record<string, unknown> | null;   // 还能改参数再批！
  reason: string | null;
}

interface AgentResult {
  status: "complete" | "pending_confirmation" | "error";
  pendingToolCalls: PendingToolCall[];
}
```

### 声明式安全（Listing 6.18–6.19）

第 5 章的危险工具清单是回调里的硬编码列表；本章改成**工具自己声明**：

```python
@tool(name="delete_file", requires_confirmation=True,
      confirmation_message="⚠️ Delete '{arguments[filename]}'? This cannot be undone.")
def delete_file(filename: str) -> str: ...
```

```typescript
// TS 装饰器语法尚不稳定，这里用高阶函数登记同样的元数据，效果等价于 Python 的 @tool
const deleteFile = tool(
  {
    name: "delete_file",
    requiresConfirmation: true,
    confirmationMessage: "⚠️ Delete '{arguments[filename]}'? This cannot be undone.",
  },
  async (filename: string): Promise<string> => {
    // ...
    throw new Error("not implemented");
  }
);
```

安全属性跟着工具走，而不是散落在使用方。

### 暂停（Listing 6.20–6.21）

`act()` 遇到 `requires_confirmation` 的调用：**不执行、不造 ToolResult**，包成 PendingToolCall 存进 `context.state["pending_tool_calls"]`。`run()` 检测到后立刻返回 `status="pending_confirmation"`，**并把 session 存盘**——进程可以退出、服务器可以重启，一切都在存储里。

### 恢复（Listing 6.22–6.23）

用户下次调用 `run(session_id=..., tool_confirmations=[...])`（注意可以不带 user_input）。`_prepare_llm_request` 发现 state 里同时有 pending 和 confirmations，交给 `_process_confirmations`：

- 批准 → `{**原参数, **modified_arguments}` 合并后执行（用户可以改参数，比如把误写的文件名改对再批）
- 拒绝/未提及 → `ToolResult(status="error", content=["Tool execution was not approved."])`

**所有结局都变成 ToolResult 进入历史**——模型恢复后看到的是一段连贯的对话，它甚至不知道中间隔了三天。完整体验：

```python
r = await agent.run("删掉 temp.txt", session_id="s1")     # → pending_confirmation
r = await agent.run(session_id="s1", tool_confirmations=[
        ToolConfirmation(tool_call_id=..., approved=True)])  # → complete
```

```typescript
let r = await agent.run("删掉 temp.txt", { sessionId: "s1" });     // → pending_confirmation
r = await agent.run(undefined, {
  sessionId: "s1",
  toolConfirmations: [{ toolCallId: "...", approved: true }],
});   // → complete
```

## 4. 长期记忆：跨会话积累经验（6.4，Listing 6.27–6.38）

目标：Agent 解 GAIA 题时能想起"以前解过类似的题，当时怎么解的、错在哪"。

### 记忆的形态：结构化而非原始日志（Listing 6.27）

```python
class TaskMemory(BaseModel):
    task_summary: str      # 题目问什么
    approach: str          # 用了什么方法和工具
    final_answer: str
    is_correct: bool
    error_analysis: str | None   # 错了的话，为什么错

    def to_embedding_text(self):
        return f"Task: {self.task_summary}"   # 只用题目做检索键！
```

```typescript
interface TaskMemory {
  taskSummary: string;            // 题目问什么
  approach: string;               // 用了什么方法和工具
  finalAnswer: string;
  isCorrect: boolean;
  errorAnalysis: string | null;   // 错了的话，为什么错
}

function toEmbeddingText(memory: TaskMemory): string {
  return `Task: ${memory.taskSummary}`;   // 只用题目做检索键！
}
```

两个设计决策值得咀嚼：① 存**提炼后的经验**而不是原始 events（原始日志又肥又噪）；② **检索键只用 task_summary**——因为检索场景是"新题来了，找相似的旧题"，用题目匹配题目，approach/结果作为 metadata 跟着走。

### 存储管线：LLM 当自己的数据工程师（Listing 6.29–6.33）

ChromaDB 要点：`collection.add(documents=...)` 传文本自动算 embedding，metadata 挂结构化字段（不能存 None，要转成 ""）。

`TaskMemoryManager.save(context)` 四步：

```
1. _format_execution_history   events → 纯文本
2. _extract_memory             LLM + response_format=TaskMemory 提炼结构化经验
3. 查重                        先向量检索 top-3 相似记忆，再让 LLM 判断 ADD/SKIP
4. collection.add              存入 ChromaDB
```

**两处都在用 LLM 管理 LLM 的记忆**：提炼靠结构化输出（第 2 章技能），查重也交给 LLM 判断——判重标准写在提示词里（"同题不同解法=新信息；同题同解法同结果=重复"），这种模糊语义判断正是 LLM 比规则代码擅长的。查重失败时的兜底是"存"（宁可重复，不可丢失）。

### 检索的两种姿势：显式工具 vs 自动注入（Listing 6.36–6.38）⭐

**姿势一（显式）**：`MemoryTool` 作为普通工具 `recall_memory` 暴露给模型，模型自己决定何时查记忆。缺点：模型经常想不起来去查。

**姿势二（自动注入）**——本章压轴设计：

```python
class MemoryTool(BaseTool):
    def __init__(self):
        super().__init__(name="recall_memory", tool_definition=None)  # ← 关键！

    async def process_llm_request(self, context, request):
        user_msgs = [c for c in request.contents if ... c.role == "user"]
        result = await self.execute(context, user_msgs[-1].content)   # 用用户问题检索
        if result:
            request.append_instructions(
                f"<PAST_EXPERIENCES>\n{result}\n</PAST_EXPERIENCES>\n"
                "Reference successful approaches and avoid approaches that led to failures.")
```

```typescript
class MemoryTool extends BaseTool {
  constructor() {
    super({ name: "recall_memory", toolDefinition: null });  // ← 关键！
  }

  async processLlmRequest(context: Context, request: LlmRequest): Promise<void> {
    const userMsgs = request.contents.filter((c) => /* ... */ c.role === "user");
    const result = await this.execute(context, userMsgs[userMsgs.length - 1].content);   // 用用户问题检索
    if (result) {
      request.appendInstructions(
        `<PAST_EXPERIENCES>\n${result}\n</PAST_EXPERIENCES>\n` +
          "Reference successful approaches and avoid approaches that led to failures."
      );
    }
  }
}
```

配套的 `_prepare_llm_request` 改造（Listing 6.38）是理解框架的钥匙：

```python

...
for tool in self.tools:
    await tool.process_llm_request(context, request)   # 但所有工具都能改造请求
```

```typescript
const llmTools = this.tools.filter((t) => t.toolDefinition !== null);  // 只有有定义的才给模型看
// ...
for (const tool of this.tools) {
  await tool.processLlmRequest(context, request);   // 但所有工具都能改造请求

```

`tool_definition=None` 的 MemoryTool 是一个**模型看不见的"工具"**：它不出现在工具清单里，模型永远不会调用它，但每次 LLM 调用前它都会自动检索相关记忆塞进提示词。"工具"的概念在此升维成了**请求处理插件**。注入的提示词还明确指示"参考成功经验、避开失败路径"——错题本比成绩单更有价值，这就是 `error_analysis` 字段存在的意义。

## 本章要带走的 5 句话

1. 记忆分三层：**执行内上下文优化（一次 run）→ Session（跨 run）→ 向量长期记忆（跨会话）**，分别解决爆上下文、会话延续、经验积累。
2. 上下文优化的铁律：**只改 request 视图，不动 events 存储**；策略分层上——先零成本的 compaction（"Re-read if needed" 占位，可重放故可丢弃），不够再上要花钱的 summarization（增量式，记住上次摘到哪）。
3. Human-in-the-loop 的正确姿势不是阻塞等输入，而是**暂停（status=pending_confirmation）→ 持久化（session）→ 恢复（tool_confirmations）**，且用户可修改参数后批准；一切结局都以 ToolResult 进历史。
4. 长期记忆存**LLM 提炼的结构化经验**（含错误分析），不存原始日志；提炼和查重都由 LLM 自己完成——模糊语义判断交给模型，管线骨架由代码把守。
5. `tool_definition=None` + `process_llm_request` 钩子 = **对模型隐形的请求处理插件**，自动把相关记忆注入每次调用——工具概念从"模型可调用的函数"升维为"参与请求构建的组件"。
