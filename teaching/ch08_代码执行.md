# 第 8 章：代码执行 —— 给 Agent 一台电脑（教学笔记）

> 对应 notebook：`notebooks/ch08/ch08_code_execution.ipynb`（Listing 8.1–8.33）
> 核心代码：`scratch_agents/tools/code_execution.py`、`skills.py`、`agent.py`（沙箱相关部分）
> 章节快照：`notebooks/ch08/{base,context,agent}.py`；需要 `E2B_API_KEY`

前七章的 Agent 只能用**你预先定义好的工具**。本章做一次范式跃迁：让 Agent **自己写代码并执行**——行动空间从"N 个固定按钮"变成"整门图灵完备的语言"。

## 1. 为什么要代码执行（8.1，Listing 8.1–8.4 为示意代码）

四个预定义工具做不到（或做得极其低效）的场景：

1. **批量处理**（Listing 8.1）：读 10 个文件再汇总 —— 工具调用要 10 轮往返（每轮一次 LLM 调用！），代码里一个 `for` 循环一轮搞定。
2. **控制流业务逻辑**（Listing 8.2）："预算内评分≥4.5 的都加购物车" —— 条件+循环+状态累积，用 tool calling 表达是灾难，用代码是 5 行。
3. **中间变量**（Listing 8.3）：pandas 清洗→分组→聚合，**中间数据留在沙箱内存里，只有最终结果回到对话** —— 这是巨大的 token 节约。工具调用模式下每个中间结果都要塞回上下文。
4. **工具组合**（Listing 8.4）：把 search_news + get_stock_price + analyze_sentiment 组合成新函数 `analyze_company` —— **Agent 现场发明新工具**。

> 一句话：tool calling 的每一步中间结果都要过一遍 LLM（慢、贵、上下文膨胀）；代码把整条流水线压进一次执行，只回传结论。

## 2. 沙箱：E2B 基础（8.2.1–8.2.2，Listing 8.5–8.8）

**为什么必须沙箱**：执行的代码是 LLM 生成的 = 不可信代码。它可能 `rm -rf`、可能泄露环境变量、可能死循环。必须隔离在用完即弃的云端微虚拟机里 —— E2B 就是干这个的。

```python
from e2b_code_interpreter import Sandbox

sandbox = Sandbox.create()                       # 开一台云端小电脑
execution = sandbox.run_code("result = 2 + 3\nprint(result)\nresult")
execution.logs.stdout     # print 输出
execution.results[0].text # 最后一个表达式的值（Jupyter 语义！）
sandbox.kill()            # 用完销毁
```

四个要点：

- **配置**（Listing 8.6）：`timeout=300` 防失控，`envs={...}` 注入 API key（沙箱里的代码也能调 Tavily 等服务）。
- **状态保持**（Listing 8.7）⭐：同一个沙箱内多次 `run_code` **共享变量** —— 第一次定义 `data = [1,2,3]`，第二次直接 `sum(data)`。它本质是一个远程 Jupyter kernel。这意味着 Agent 可以多步迭代地做数据分析，不用每次重来。
- **错误结构化**（Listing 8.8）：`execution.error.name / .value`（如 ZeroDivisionError）—— 错误不是崩溃，是数据，接下来会喂回给模型。

## 3. 接进框架：三个部件（8.2.3–8.2.4，Listing 8.9–8.14）

改动模式和第 6 章一模一样 —— context 加字段、Agent 加参数、_setup_tools 自动注入工具：

```python
# ① ExecutionContext 加一个字段
code_env: Optional[Sandbox] = None

# ② Agent 加一个参数，_setup_tools 里自动追加 execute_python 工具
Agent(..., code_execution="e2b")

# ③ run() 里管理生命周期
if self.code_execution == "e2b" and context.code_env is None:
    context.code_env = Sandbox.create(timeout=300)
try:
    ...  # 主循环
finally:
    if context.code_env is not None:
        context.code_env.kill()      # 无论成败都销毁，不留付费资源
```

工具本体（Listing 8.13）就是把两者接起来：

```python
@tool(name="execute_python", description="Execute Python code in a sandboxed environment...")
def execute_python(context: ExecutionContext, code: str) -> str:
    sandbox = context.code_env          # ← 沙箱通过 context 注入（第4章设计的回报）
    execution = sandbox.run_code(code)
    return json.dumps(execution.to_json(), ...)   # stdout/结果/错误全部回传给模型
```

测试（Listing 8.14）：`tools=[]` 什么都不给，只开 `code_execution="e2b"`，问"第 100 个斐波那契数"—— 模型自己写循环算出来。**一个 execute_python = 无限个潜在工具。**

## 4. 工具传送进沙箱：sandbox_executable（8.3，Listing 8.15–8.22）⭐

新问题：Agent 在沙箱里写代码时，能不能**在代码里**直接调用我们写好的工具函数？比如在循环里调 `get_wikipedia_revisions()`。这就是"工具的可移植性"。

### 机制三步走

**① 标记**（Listing 8.15）：`FunctionTool(func, sandbox_executable=True)`。硬约束：**不能带 context 参数**（沙箱里没有 ExecutionContext，构造时直接 raise）—— 沙箱工具必须是自包含的纯函数。

**② 源码提取**（Listing 8.16）：`inspect.getsource(self.func)` 拿到函数源码，再逐行剥掉 `@tool` 装饰器（沙箱里没有这个装饰器，留着会 NameError）。**函数以源代码文本的形式被"传送"**。

**③ 预注册**（Listing 8.20）：沙箱创建时把所有 sandbox 工具的源码拼起来 `run_code` 一次 —— 因为沙箱是持久 kernel，这些函数从此常驻，后续任何代码都能直接调用。

### 告诉模型（Listing 8.21）

光注册还不够，模型得知道这些函数存在：

```python
def _get_sandbox_tools_prompt(self) -> str:
    return ("\n\n## Sandbox-Executable Tools\n"
            "The following functions are pre-registered in the sandbox "
            "and can be called directly in your Python code:\n"
            f"{tools_json}")     # 复用同一份 tool_definition JSON！
```

至此工具分成了**两个层级**：

| | 谁调用 | 怎么调用 | 一次能干多少 |
|---|---|---|---|
| 普通工具 | LLM 通过 tool calling | 一轮一次 | 一个动作 |
| sandbox 工具 | **Agent 写的代码** | 循环/组合随便用 | 任意复杂的流水线 |

同一份 `tool_definition` JSON 两用：一份进 tools 参数（教模型怎么发 ToolCall），一份进 system prompt（教模型在代码里怎么调函数）。

### 实战（Listing 8.17、8.22）

`get_wikipedia_revisions` 注意一个细节：**`import requests` 写在函数体内** —— 源码传送后要在沙箱里自包含运行，依赖必须随函数走。

测试题是 GAIA 的硬题："2023 年 6 月底版本的英文维基'八月每一天'页面里，有多少引用了 Twitter/X？" —— 需要循环 31 个页面、每个抓历史版本、正则数引用。tool calling 模式要 31+ 轮往返；sandbox 工具模式下模型写一个 for 循环一次搞定。

Excel 分析实战（Listing 8.26）：把 GAIA 的 xlsx 上传进沙箱，Agent 自己 `pip list` 检查、用 pandas 读表、分组求和、比较两城市销售额。对比第 5 章的 `read_file`（只能整表转 markdown 塞给模型），现在**数据在沙箱里加工，模型只看结论** —— 这就是 8.1 说的"中间变量"优势的实战版。

## 6. Agent Skills：渐进式披露（8.5，Listing 8.27–8.33）⭐

最后一个问题：有些"能力"不是一个函数，而是**一套操作知识**（用什么库、什么步骤、什么坑）。全塞 system prompt？太占 token 且大部分时候用不上。

**Skill = 一个装着 SKILL.md 的文件夹**：

```
skills/
└── pdf-merge/
    └── SKILL.md      # YAML frontmatter(name, description) + markdown 正文（用法教程）
```

```markdown
---
name: pdf-merge
description: Merge multiple PDF files into a single PDF document. Use when the user wants to combine, merge...
---
# PDF Merge
## Usage
```python
from pypdf import PdfWriter, PdfReader
...完整示例代码...
```
```

实现三件套（Listing 8.28–8.30）：`parse_frontmatter`（正则抽 YAML 头）→ `load_skill`/`discover_skills`（扫目录）→ `generate_skills_prompt`。

**核心思想——渐进式披露（progressive disclosure）**：

```
系统提示词里只放：  name + description（一行）+ "用前先 cat SKILL.md"
模型判断需要时才：  cat /home/user/skills/pdf-merge/SKILL.md   ← 用 bash_tool！
然后照着文档写代码： 在沙箱里执行
```

三层 token 成本：**清单（几十 token，常驻）→ 文档（几百 token，按需）→ 执行（不占对话）**。description 写得好坏决定模型能不能在对的时机想起这个技能——所以 description 里要写触发场景（"Use when the user wants to combine, merge, concatenate..."）。

集成很轻：`Agent(skills_path="./skills")`，沙箱创建时把 skill 文件夹上传到 `/home/user/skills/`，提示词自动生成。

> 观念转变：**Skill 不是代码，是写给 Agent 看的文档。** 扩展 Agent 能力从"写函数注册工具"变成"写一篇 markdown 教程"——不用改任何代码。（Claude Code 的 skills 机制就是同一个思想。）

8.5.5 收尾给出完整的层级：**普通工具（LLM 直调）→ execute_python（写代码）→ sandbox 函数（代码里调）→ skills（按需读文档学新能力）** —— 能力的粒度和披露时机逐层递进。

---

## 本章要带走的 5 句话

1. 代码执行把行动空间从"N 个按钮"扩展成"图灵完备语言"：批量循环、控制流、**中间数据留在沙箱只回传结论**、现场组合新工具。
2. LLM 生成的代码 = 不可信代码，必须进沙箱（E2B）；沙箱是**持久的远程 Jupyter kernel**（跨执行共享变量），生命周期用 try/finally 兜底销毁。
3. `sandbox_executable` 工具通过 **inspect 提取源码 → 剥装饰器 → 预注册进沙箱**，让 Agent 能在自己写的代码里循环调用你的函数；约束是无 context、import 写函数内（自包含）。
4. 工具从此两层：LLM 直调的普通工具（一轮一动作）vs 代码内调用的沙箱函数（一轮一条流水线）；同一份 tool_definition JSON 既进 tools 参数也进 system prompt。
5. Skills = SKILL.md 文件夹 + **渐进式披露**：清单常驻（几十 token）、文档按需 cat、执行不占上下文——扩展能力从写代码变成写文档。
