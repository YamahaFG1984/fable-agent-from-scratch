## 1. 问题：ReAct 的短视（7.1，纯概念节）

第 4 章的 ReAct 循环是"走一步看一步"：每次只看眼前的历史决定下一个动作。面对多步复杂任务，暴露四种失败模式：

1. **迷路**——步骤多了忘记最初目标，在细节里打转
2. **重复劳动**——忘了某信息已查过，再查一遍
3. **死磕**——一个工具反复失败，还是反复调它
4. **草率收官**——信息还不全就急着给答案

人类专家怎么对付这类问题？**先规划（写待办清单），中途反思（停下来检查方向）。** 本章把这两个认知行为做成工具。

## 2. Planning：create_tasks 工具（7.2，Listing 7.1–7.3）

### Task 数据结构（Listing 7.1）

```python
class Task(BaseModel):
    content: str
    status: Literal["pending", "in_progress", "completed"]

    def __str__(self):
        if self.status == "pending":     return f"[ ] {self.content}"
        elif self.status == "in_progress": return f"[>] **{self.content}**"
        elif self.status == "completed":   return f"[x] ~~{self.content}~~"
```

```typescript
type TaskStatus = "pending" | "in_progress" | "completed";

class Task {
  content: string;
  status: TaskStatus;

  constructor(content: string, status: TaskStatus) {
    this.content = content;
    this.status = status;
  }

  toString(): string {
    if (this.status === "pending") return `[ ] ${this.content}`;
    else if (this.status === "in_progress") return `[>] **${this.content}**`;
    else return `[x] ~~${this.content}~~`;
  }
}
```

`__str__` 渲染成 markdown 待办清单（未做/进行中加粗/已完成划掉）——记住第 5 章的准则：**输出为 LLM 消费而格式化**，视觉化的清单比 JSON 更能让模型"看见"进度。

### 工具本体（Listing 7.2）——注意它多么"无能"

```python
@tool
def create_tasks(tasks: List[Task]) -> str:
    """Create or update a task plan.
    WHEN TO USE: 复杂多步研究、需要综合多来源的问题
    WHEN NOT TO USE: 一次搜索能答的简单问题
    HOW TO USE: 每次重新生成整个清单并更新状态；
                完成的标 completed，下一个标 in_progress，其余 pending
    """
    return "\n".join(str(task) for task in tasks)
```

```typescript
import { z } from "zod";

// TS 用函数 + 显式的 tool 定义对象来达到 Python @tool 装饰器的效果
const TaskSchema = z.object({
  content: z.string(),
  status: z.enum(["pending", "in_progress", "completed"]),
});

function createTasksImpl(tasks: Task[]): string {
  return tasks.map((task) => task.toString()).join("\n");
}

const createTasks = {
  name: "create_tasks",
  description: `Create or update a task plan.
WHEN TO USE: 复杂多步研究、需要综合多来源的问题
WHEN NOT TO USE: 一次搜索能答的简单问题
HOW TO USE: 每次重新生成整个清单并更新状态；
            完成的标 completed，下一个标 in_progress，其余 pending`,
  schema: z.object({ tasks: z.array(TaskSchema) }),
  execute: createTasksImpl,
};
```

**函数体就一行格式化**。没有数据库、没有调度器、不存任何东西。那它凭什么有用？

三层机制：

1. **强迫先想后做**——要调用这个工具，模型必须先生成完整任务分解。规划这个动作本身改变了后续生成的质量（相当于给推理"预热"）。
2. **计划进入历史**——返回的清单成为 ToolResult 留在 events 里，之后每一步模型都能看到"全局地图"，不再只凭最近几条消息导航。这治好了"迷路"和"重复劳动"。
3. **状态更新即自查**——docstring 要求"每次重新生成整个清单"，模型更新状态时被迫盘点：哪些做完了？下一步是什么？

**docstring 才是本体**：WHEN TO USE / WHEN NOT TO USE / HOW TO USE 三段完全是写给模型的行为指南。第 3 章说"工具描述是提示词工程"，本章把它推到极致——**工具描述就是全部功能**。WHEN NOT TO USE 同样重要：简单问题也列计划纯属浪费 token（过度规划是真实的失败模式）。

## 3. Reflection：反思工具（7.3，Listing 7.4）

```python
@tool
def reflection(analysis: str, need_replan: bool = False) -> str:
    """Pause and analyze progress before continuing.
    WHEN TO USE:
      1. PROGRESS REVIEW  —— 完成一个阶段后（"纪录已查到 2:01:09，转向月球距离"）
      2. ERROR ANALYSIS   —— 工具失败时（"Wikipedia 挂了，原因：服务不可用，改用 web 搜索"）
      3. RESULT SYNTHESIS —— 综合多来源信息时（"查到两个月球距离，题目问最近距离，用近地点 356,500km"）
      4. SELF CHECK       —— 给最终答案前（"配速 20.81km/h、距离 356,500km 都有了，可以计算了"）
    WHEN NOT TO USE: 每次工具调用后都反思（纯开销）、一切顺利时
    """
    if need_replan:
        return f"Reflection recorded (REPLAN NEEDED): {analysis}"
    return f"Reflection recorded: {analysis}"
```

```typescript
// TS 用函数 + 显式的 tool 定义对象来达到 Python @tool 装饰器的效果
function reflectionImpl(analysis: string, needReplan: boolean = false): string {
  if (needReplan) {
    return `Reflection recorded (REPLAN NEEDED): ${analysis}`;
  }
  return `Reflection recorded: ${analysis}`;
}

const reflection = {
  name: "reflection",
  description: `Pause and analyze progress before continuing.
WHEN TO USE:
  1. PROGRESS REVIEW  —— 完成一个阶段后（"纪录已查到 2:01:09，转向月球距离"）
  2. ERROR ANALYSIS   —— 工具失败时（"Wikipedia 挂了，原因：服务不可用，改用 web 搜索"）
  3. RESULT SYNTHESIS —— 综合多来源信息时（"查到两个月球距离，题目问最近距离，用近地点 356,500km"）
  4. SELF CHECK       —— 给最终答案前（"配速 20.81km/h、距离 356,500km 都有了，可以计算了"）
WHEN NOT TO USE: 每次工具调用后都反思（纯开销）、一切顺利时`,
  schema: z.object({
    analysis: z.string(),
    needReplan: z.boolean().default(false),
  }),
  execute: ({ analysis, needReplan }: { analysis: string; needReplan?: boolean }) =>
    reflectionImpl(analysis, needReplan),
};
```

比 create_tasks 更极端——**它连格式化都算不上，就是把输入原样回显**。价值全在于：

- **调用即思考**：为了填 `analysis` 参数，模型必须先组织一段对现状的分析。这段分析随 ToolCall 进入历史，成为后续决策的显式依据。等价于在行动流里强制插入一步"写下来的思考"（写下来的思考比隐式思考更可靠，且对后续每一步可见）。
- `need_replan` 标志给了模型一个正式的"掀桌子"通道——宣告当前计划作废，需要重规划。
- docstring 的四个场景各配一个**示例句**，教模型好的反思长什么样（few-shot 藏在工具描述里）。

### 失败恢复实验（7.3.3，Listing 7.5–7.6）——本章最精彩的实验

故意造一个必挂的工具：

```python
@tool
def get_wikipedia_page(title: str) -> str:
    """Get a Wikipedia page by title."""
    raise RuntimeError("Wikipedia service is temporarily unavailable")

agent = Agent(tools=[get_wikipedia_page, search_web, reflection],
              instructions="Always try Wikipedia first when researching topics.",  # 故意把模型往坑里带
              max_steps=5)
```

```typescript
// TS 用函数 + 显式的 tool 定义对象来达到 Python @tool 装饰器的效果
function getWikipediaPageImpl(title: string): string {
  throw new Error("Wikipedia service is temporarily unavailable");
}

const getWikipediaPage = {
  name: "get_wikipedia_page",
  description: "Get a Wikipedia page by title.",
  schema: z.object({ title: z.string() }),
  execute: getWikipediaPageImpl,
};

const agent = new Agent({
  tools: [getWikipediaPage, searchWeb, reflection],
  instructions: "Always try Wikipedia first when researching topics.",  // 故意把模型往坑里带
  maxSteps: 5,
});
```

指令故意引导模型先用 Wikipedia。没有 reflection 的 Agent 常见行为：反复重试挂掉的工具直到烧光步数（失败模式 3"死磕"）。有 reflection 的行为链：

```
调 Wikipedia → 收到 error ToolResult（第 4 章的错误哲学在此接力）
→ 调 reflection("Wikipedia 失败，原因：服务不可用，替代方案：web 搜索")
→ 调 search_web → 得到答案
```

注意分工：**第 4 章的错误处理让模型"看得见"失败（error 进历史），本章的 reflection 让模型"消化"失败（显式分析原因并规划替代路径）**。看见 ≠ 消化，reflection 补上了后半截。

### 研究综合实验（7.3.4，Listing 7.7）

开放型任务（"调研量子计算最新进展"）没有唯一答案，reflection 扮演 RESULT SYNTHESIS 角色：多次搜索之间停下来盘点"已覆盖哪些方面、还缺哪些视角"，最终报告的结构性明显更好。

## 4. 整合：失败模式 → 对症工具（7.4，概念节）

| ReAct 失败模式 | 解药 |
|---|---|
| 迷路（忘记目标） | Planning（全局地图常驻历史） |
| 重复劳动 | Planning（清单标记了已完成） |
| 死磕失败工具 | Reflection（ERROR ANALYSIS 强制换路） |
| 草率收官 | Reflection（SELF CHECK 先盘点再作答） |

两者组合使用：开局 create_tasks 定方向，中途 reflection 纠偏，`need_replan=True` 时回头更新任务清单——形成"规划 → 执行 → 反思 → 重规划"的完整认知闭环。

---

## 本章要带走的 5 句话

1. ReAct 天生短视，四大失败模式：迷路、重复劳动、死磕失败工具、草率收官——解药是把人类专家的"先规划、中反思"移植给 Agent。
2. `create_tasks` 和 `reflection` 都是**空壳工具**：函数体近乎无操作，全部价值在于**调用它们的行为强迫模型生成结构化思考，并把思考留在历史里**。
3. 工具的 docstring 就是行为编程：WHEN TO USE / WHEN NOT TO USE / 场景示例——这是提示词工程的最高形态，WHEN NOT TO USE 防止过度规划/过度反思的开销。
4. 失败恢复 = 第 4 章"错误进历史"（让模型看见）+ 本章 reflection（让模型消化：析因 + 换路）。
5. 认知闭环：**规划定方向 → 执行 → 反思纠偏 →（need_replan 时）重规划**——不改一行框架代码，纯靠两个提示词工具实现。
