## 1. Agent 评估为什么难（10.1）

传统软件测试的前提在 Agent 身上全部失效：

- **不确定性**：同一输入两次运行，路径和措辞都可能不同——没法断言 `output == expected`
- **开放式输出**："调研量子计算进展"没有唯一正确答案
- **过程也重要**：答案对但引用了假来源、烧了 50 步才做完，算好吗？

于是评估分两条路线，本章两条都走：

| 路线 | 适用 | 本书实现 |
|------|------|---------|
| **精确匹配基准** | 有标准答案的封闭任务 | GAIA + `is_correct`（第 2 章起用到现在） |
| **LLM-as-Judge** | 开放式输出 | 三个维度的评审提示词 |

## 2. LLM-as-Judge：让模型当裁判（10.1–10.4）

核心想法：既然人能读一段回答判断好坏，而 LLM 能模拟人的判断——**用一个 LLM 给另一个 LLM 的输出打分**。框架就是一组精心设计的提示词（`eval/prompts.py`）：

**裁判的"法官守则"（EVALUATION_SYSTEM_PROMPT）**：

```
You are an evaluation judge for AI agent responses.
Provide fair, consistent, and detailed evaluations.
Always explain your reasoning.
```

最后一句最重要：**强制说理**。要求裁判先解释再打分，既提升判分质量（推理让评分更稳定），也让分数可审计——你能看出裁判是不是判错了。

### 三个评估维度（10.2–10.4）

**① Answer Relevancy 答案相关性** —— 最基础的问题：答非所问吗？

```
输入：question + answer
量表：1（完全不相关）→ 5（高度相关），附解释
```

**② Citation Reliability 引用可靠性** —— 针对 Agent 特有的风险：会搜索的 Agent 也会**编造来源**。

```
输入：question + answer + sources
检查：1. 来源真实可访问吗？ 2. 来源支持答案里的论断吗？ 3. 来源对该主题权威吗？
```

三个子问题层层递进：来源存在 ≠ 来源相关 ≠ 来源权威。这是对"幻觉引用"的针对性防御。

**③ Requirement Compliance 需求合规性** —— 答对了但没按要求答，也算失败。

```
输入：question + requirements（如"100词以内、含至少一个例子、用英文"）+ answer
检查：1. 覆盖问题所有部分？ 2. 遵守指定格式？ 3. 满足所有约束？
```

三个维度正交：一个回答可以高度相关（5 分）但引用是编的（1 分）且超了字数（2 分）。**单一分数会掩盖问题，多维度才能定位问题。**

### 运行方式（notebook 10.2–10.4）

评估复用自家框架的 `LlmClient`——填模板 → 装进 `LlmRequest` → `generate()`。没有引入任何评估库：**评估基础设施 = 提示词 + 你已有的 LLM 客户端**。

实践注意（书中原则）：裁判模型最好 ≠ 被评模型（避免"自己给自己打分"的偏袒），且裁判要用足够强的模型——裁判不可靠，一切分数无意义。

## 3. OPR：把多维分数聚合成一个数字（10.5）

工程团队需要一个能进仪表盘、能设门禁的单一数字：

```python
OPR = 通过的评估数 / 总评估数

evaluation_results = [
    {"metric": "answer_relevancy",      "score": 0.95, "passed": True},
    {"metric": "citation_reliability",  "score": 0.80, "passed": True},
    {"metric": "requirement_compliance","score": 0.60, "passed": False},
    ...
]
opr = sum(r["passed"] for r in results) / len(results)   # → 60%
```

```typescript
// OPR = 通过的评估数 / 总评估数

const evaluationResults = [
  { metric: "answer_relevancy",       score: 0.95, passed: true },
  { metric: "citation_reliability",   score: 0.80, passed: true },
  { metric: "requirement_compliance", score: 0.60, passed: false },
  // ...
];
const opr = results.filter((r) => r.passed).length / results.length;   // → 60%
```

两个层次的用法：

- **总 OPR**：一个数字，回答"这个 Agent 总体多可靠"——用于版本对比、回归门禁（"OPR 不得低于上版"）
- **按维度分解**（`defaultdict` 分组统计）：回答"差在哪"——relevancy 100% 但 citation 50%，说明问题不在理解而在引用习惯，该改的是提示词里的引用规范

注意 `score` → `passed` 的转换隐含了**阈值决策**（比如 ≥0.7 算过）：连续分数用于诊断，布尔通过用于门禁，两者用途不同。

## 4. GAIA 终局评测：回到起点（10.6）

全书首尾呼应的时刻。第 2 章用裸 LLM 跑 GAIA（很多题只能答"unsolvable"），现在用满配 Agent 再跑同一基准：

```python
agent = Agent(model=..., tools=[calculator], instructions=..., max_steps=5)

for tc in test_cases:
    result = await agent.run(tc["question"])
    correct = is_correct(str(result.output), tc["answer"])   # strip + lower 后精确匹配
```

```typescript
const agent = new Agent({
  model: /* ... */,
  tools: [calculator],
  instructions: /* ... */,
  maxSteps: 5,
});

for (const tc of testCases) {
  const result = await agent.run(tc.question);
  const correct = isCorrect(String(result.output), tc.answer);   // trim + toLowerCase 后精确匹配
}
```

评测循环极简：跑 → 精确匹配 → 算准确率。`is_correct` 还是第 2 章那个函数（大小写不敏感的精确匹配）——GAIA 的题面设计保证了答案是短事实（数字/短语），所以敢用精确匹配；这也解释了第 2 章 gaia_prompt 里那些"数字不要带逗号和单位"的格式指令——**基准的评分方式反向决定了提示词的写法**。

由此得到全书的完整实验弧线：

```
第2章  裸 LLM         → 基线（大量 unsolvable）
第4章  + 工具 + 循环   → 能解需要检索的题
第5章  + 文件工具      → 能解带附件的题
第6章  + 记忆          → 能从错题中学习
第8章  + 代码执行      → 能解需要计算/批处理的题
第10章 终局评测        → 同一把尺子量出每次进化的增益
```

**同一个基准贯穿全书**不是偷懒，是方法论：固定度量，才能归因每个组件的贡献。

## 5. 监控视角（章节标题的另一半）

书中把评估延伸到线上：离线评估（发版前跑基准）之外，还需要在线监控——第 4 章的 `display_trace`、`usage_metadata`（token 统计）、`AgentResult.context`（完整事件历史）都是为此准备的原材料。**events 记录一切**的架构决策，最终在可观测性上收获完整回报：每一次生产运行都自带可回放的审计日志。

---

## 本章要带走的 5 句话

1. Agent 评估两条路线：**封闭任务用精确匹配基准（GAIA），开放输出用 LLM-as-Judge**。
2. LLM-as-Judge 的关键是提示词工程：法官守则 + **强制说理**（先解释后打分，可审计）；裁判模型要强、最好不同于被评模型。
3. 三维正交评估——相关性、引用可靠性（防幻觉引用的三连问）、需求合规性——**单一分数掩盖问题，多维度定位问题**。
4. OPR = 通过数/总数：总值做回归门禁，按维度分解做诊断；score→passed 的阈值转换分开了"诊断用连续分"和"门禁用布尔值"。
5. 全书用同一个 GAIA 基准从第 2 章量到第 10 章——**固定度量才能归因每个组件的贡献**；而 events 记录一切的架构让每次运行自带审计日志。
