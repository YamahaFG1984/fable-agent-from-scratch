## 1. 为什么要多智能体（9.1）

单个 Agent 什么都干会遇到三堵墙：**工具太多**（几十个工具定义挤爆上下文，模型选择准确率下降）、**指令冲突**（"你是严谨的代码审查员"和"你是发散的创意作家"没法共存于一个 system prompt）、**上下文互相污染**（研究的长篇材料淹没编码任务）。解法和人类组织一样：**专业分工**——每个 Agent 少量工具、单一职责、干净指令。

问题变成：分工后怎么协作？本章给出三种模式 + 一个跨网络协议。

## 2. 三种协作模式总览（9.2，Listing 9.1–9.3）

| 模式 | 谁决定流程 | 上下文 | 控制权 | 类比 |
|------|-----------|--------|--------|------|
| **Workflow** | 开发者（代码写死） | 共享一个 context | 编排器 | 流水线 |
| **Agent as Tool** | 调用方 LLM 按需委托 | **隔离**（子agent新开context） | 始终在调用方 | 打电话咨询专家 |
| **Transfer** | LLM 动态路由 | **共享**（整个 context 移交） | **移交**给目标 | 转接客服 |

选择心法：流程固定用 Workflow（确定性、可测试）；需要"问一下专家再回来"用 Agent-as-Tool；需要"这事归你管了"用 Transfer。三者可以嵌套组合。

## 3. Workflow：代码定义顺序（9.3，Listing 9.4–9.7）

先看一个关键设计（Listing 9.4）：**三个 Workflow 都继承 Agent**。

```python
class SequentialWorkflow(Agent): ...
class ParallelWorkflow(Agent): ...
class LoopWorkflow(Agent): ...
```

```typescript
class SequentialWorkflow extends Agent { /* ... */ }
class ParallelWorkflow extends Agent { /* ... */ }
class LoopWorkflow extends Agent { /* ... */ }
```

它们不调 LLM、不用工具，只覆写 `run()`。继承的意义是**组合律**：Workflow 拥有和 Agent 一样的 `run()` 签名，所以 Workflow 里可以套 Workflow、Workflow 可以被 AgentTool 包装、可以当 sub_agent——整个体系闭合了。

### Sequential（Listing 9.5）：接力棒

```python
for i, agent in enumerate(self.agents):
    if context is not None:
        context.final_result = None    # ← 关键！
        context.current_step = 0       # ← 关键！
    if i == 0:
        result = await agent.run(user_input, context=context)
    else:
        result = await agent.run(context=context)   # 不传 user_input！
    context = result.context
```

```typescript
for (let i = 0; i < this.agents.length; i++) {
  const agent = this.agents[i];
  if (context !== null) {
    context.finalResult = null;    // ← 关键！
    context.currentStep = 0;       // ← 关键！
  }
  let result: AgentResult;
  if (i === 0) {
    result = await agent.run(userInput, context);
  } else {
    result = await agent.run(undefined, context);   // 不传 user_input！
  }
  context = result.context;
}
```

两个必须理解的细节：

1. **每棒之前重置 `final_result` 和 `current_step`**——上一个 agent 结束时把 final_result 设了值，不清掉的话下一个 agent 的 while 循环一步都不会跑。
2. **只有第一个 agent 收 user_input**——后面的 agent 打开共享 context 就能看到全部历史（用户问题 + 前手的所有工作），它的"任务"由自己的 instructions 定义（如"审查上文中的代码"）。

### Loop（Listing 9.7）：迭代收敛

```python
StopCondition = Callable[[AgentResult, int], bool]   # (当前结果, 轮数) -> 停不停

for iteration in range(1, self.max_iterations + 1):
    for agent in self.agents:        # 一轮 = 顺序跑一遍所有 agent
        ...
    if self.stop_condition and self.stop_condition(result, iteration):
        break
```

```typescript
type StopCondition = (result: AgentResult, iteration: number) => boolean;   // (当前结果, 轮数) -> 停不停

for (let iteration = 1; iteration <= this.maxIterations; iteration++) {
  for (const agent of this.agents) {        // 一轮 = 顺序跑一遍所有 agent
    // ...
  }
  if (this.stopCondition && this.stopCondition(result, iteration)) {
    break;
  }
}
```

典型用法：`[writer, reviewer]` 循环，stop_condition 检查 reviewer 输出里有没有 "APPROVED"。`max_iterations` 是保险丝——**和第 4 章 max_steps 同一哲学：凡是可能不收敛的循环都要有上限。**

## 4. Agent as Tool：把 Agent 包装成工具（9.4，Listing 9.8–9.9）

第 5 章 `read_media_file` 在工具里调 LLM，第 8 章 skill 在沙箱里干活——本章把这个委托思想推到顶：**整个 Agent 就是一个工具**。

```python
class AgentTool(BaseTool):
    def __init__(self, agent, input_schema=None):
        # agent.name → 工具名，agent.description → 工具描述
        # 参数：默认一个 request 字符串；或传 Pydantic input_schema 生成结构化参数
        tool_def = format_tool_definition(agent.name, agent.description, parameters)
        super().__init__(name=agent.name, description=agent.description, tool_definition=tool_def)

    async def execute(self, context, **kwargs):
        request = ...                        # kwargs → 请求文本
        result = await self.agent.run(request)   # ← 注意：没传 context！
        return result.output                      # ← 只返回最终输出
```

```typescript
class AgentTool extends BaseTool {
  private agent: Agent;

  constructor(agent: Agent, inputSchema?: ZodSchema) {
    // agent.name → 工具名，agent.description → 工具描述
    // 参数：默认一个 request 字符串；或传 zod inputSchema 生成结构化参数
    const toolDef = formatToolDefinition(agent.name, agent.description, parameters);
    super({ name: agent.name, description: agent.description, toolDefinition: toolDef });
    this.agent = agent;
  }

  async execute(context: ExecutionContext, kwargs: Record<string, any>): Promise<any> {
    const request = /* ... */;                          // kwargs → 请求文本
    const result = await this.agent.run(request);       // ← 注意：没传 context！
    return result.output;                                // ← 只返回最终输出
  }
}
```

`execute` 的两行藏着本模式的灵魂——**上下文隔离**（9.4.3）：

1. `self.agent.run(request)` 不传 context → 子 Agent 在**全新的 ExecutionContext** 里跑，看不到调用方的历史；
2. `return result.output` → 子 Agent 内部的几十步搜索、工具调用、中间结果**全部不回流**，调用方只看到一句结论。

好处：调用方上下文不被污染（这正是 9.1 的痛点三）；代价：子 Agent 不知道大局，请求文本必须自包含。这是**信息封装**的经典取舍。

实战（Listing 9.9）：researcher（带 search_web）+ coder（带 code_execution）包成两个工具给一个 assistant——assistant 自己一个真工具都没有，纯靠委托。

## 5. Transfer：控制权移交（9.5，Listing 9.10–9.18）⭐

Agent-as-Tool 是"咨询后拿回话筒"；Transfer 是"话筒直接给你"。适合客服路由类场景：分诊后就该由专家全程接管，没必要回到路由器。

### 转移目标 = 树上的邻居（Listing 9.12）

```python
def _get_transfer_targets(self):
    targets = list(self.sub_agents)          # 孩子：可以下派
    if self.parent:
        targets.append(self.parent)          # 父亲：可以上报
        if not self.disallow_transfer_to_peers:
```

```typescript
private getTransferTargets(): Agent[] {
  const targets: Agent[] = [...this.subAgents];          // 孩子：可以下派
  if (this.parent) {
    targets.push(this.parent);                           // 父亲：可以上报
    if (!this.disallowTransferToPeers) {
      targets.push(
        ...this.parent.subAgents.filter((s) => s.name !== this.name)  // 兄弟：可以平转
      );
    }
  }
  return targets;

```

`disallow_transfer_to_peers` 强制"层级汇报制"（必须经过父级中转）。查找目标时 `_find_agent` 先爬到根再 DFS 全树（Listing 9.13）——任何位置都能找到任何 agent。

## 6. A2A：跨网络协作（9.6，无编号 listing）

前面的模式都要求 agents 在同一进程。A2A（Agent-to-Agent）协议把协作扩展到网络：不同机器、不同框架、不同公司的 agent 互通。MCP 标准化"agent↔工具"，A2A 标准化"agent↔agent"。

两个核心概念：

**Agent Card**——服务发现。约定 URL `/.well-known/agent.json` 返回 agent 的名字、描述、能力。`RemoteAgent`（`remote.py`）初始化时抓这个卡片：

```python
class RemoteAgent:
    def __init__(self, base_url):
        # GET {base_url}/.well-known/agent.json → self.name, self.description
    async def run(self, user_input, ...):
        # POST /tasks/send，JSON-RPC 2.0：
        # {"method": "tasks/send", "params": {"message": {"role": "user", "parts": [{"type": "text", ...}]}}}
        # 响应从 result.artifacts[].parts[] 里抽文本
        return AgentResult(output=output, context=context)
```

```typescript
class RemoteAgent {
  baseUrl: string;
  name!: string;
  description!: string;

  private constructor(baseUrl: string) {
    this.baseUrl = baseUrl;
  }

  // JS 构造函数不能是 async，用静态工厂方法代替 Python __init__ 里直接同步抓卡片的写法
  static async create(baseUrl: string): Promise<RemoteAgent> {
    const agent = new RemoteAgent(baseUrl);
    const res = await fetch(`${baseUrl}/.well-known/agent.json`);   // GET {base_url}/.well-known/agent.json
    const card = await res.json();
    agent.name = card.name;
    agent.description = card.description;
    return agent;
  }

  async run(userInput: string, context?: ExecutionContext): Promise<AgentResult> {
    // POST /tasks/send，JSON-RPC 2.0：
    const res = await fetch(`${this.baseUrl}/tasks/send`, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({
        jsonrpc: "2.0",
        method: "tasks/send",
        params: {
          message: { role: "user", parts: [{ type: "text", text: userInput }] },
        },
      }),
    });
    const { result } = await res.json();
    // 响应从 result.artifacts[].parts[] 里抽文本
    const output = result.artifacts
      .flatMap((a: { parts: { text: string }[] }) => a.parts)
      .map((p: { text: string }) => p.text)
      .join("");
    return { output, context };
  }
}
```

**关键设计：RemoteAgent 的 `run()` 签名和本地 Agent 一致**——所以它能被 AgentTool 包装、能进 Workflow，调用方无感知远近。这是第 4 章"MCP 工具和本地函数无差别"思想在 agent 层的复刻。

服务端（`a2a_server.py`）：`MathAgentExecutor` 把本地 Agent 适配成 A2A 服务——从协议消息里抽用户文本 → `agent.run()` → 结果包成 artifact 推给事件队列。

## 本章要带走的 5 句话

1. 单 Agent 的三堵墙——工具过多、指令冲突、上下文污染——解法是专业分工 + 三种协作模式。
2. 三种模式一句话分清：**Workflow 代码定流程（共享 context）；Agent-as-Tool 咨询后收回控制（隔离 context，只回结论）；Transfer 移交控制权（整个 context 带走，不回头）**。
3. Workflow 继承 Agent 是为了**组合律**：工作流可嵌套、可被包装成工具、可当子 agent；Sequential 的两个坑——换棒时清 final_result/current_step、只有第一棒收 user_input。
4. Transfer 的工程细节全是防错设计：名字唯一、单一父级、enum 锁死目标名单、先到先得、工具只设标志而移交在 run() 层执行。
5. A2A 用 Agent Card（`/.well-known/agent.json`）+ JSON-RPC 把协作扩展到跨网络，而 `RemoteAgent.run()` 与本地签名一致——**远程 agent 用起来和本地没有区别**。
