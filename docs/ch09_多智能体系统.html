编排多智能体系统

单个 Agent 什么都干会撞上三堵墙：工具太多、指令冲突、上下文互相污染。解法和人类组织一样——专业分工。问题变成：分工后怎么协作？

9.1三种协作模式：谁拿着"话筒"

9.2Workflow：三种继承 Agent 的编排器

SequentialWorkflow、ParallelWorkflow、LoopWorkflow 全部继承 Agent——它们不调 LLM、不用工具，只覆写 run()。继承的意义是组合律：Workflow 拥有和 Agent 一样的 run() 签名，所以能嵌套、能被包装成工具、能当子 Agent，整个体系因此闭合。Sequential 换棒时有两个必须记住的细节：每棒之前要重置 final_result 和 current_step（否则下一个 Agent 的循环一步都不会跑），且只有第一个 Agent 收到 user_input，后面的 Agent 靠打开共享 context 看到全部历史。

9.3Transfer：路由菜单 + 树形结构

Agent 组成一棵树（sub_agents / parent），transfer_to_agent 工具的参数被加上 enum 约束——模型只能从合法的 Agent 名单里选，堵死幻觉出一个不存在的名字。工具本身只设一个标志位（context.transfer_to = agent_name），真正的移交动作发生在 run() 循环层面：检测到标志后把整个 context 传给目标 Agent 的 run()，当前 Agent 退出循环。

9.4A2A：跨网络的 Agent 协作

前面的模式都要求 Agent 在同一进程里。A2A（Agent2Agent）协议把协作扩展到网络：约定 /.well-known/agent.json 做服务发现（返回名字、描述、能力），再用 JSON-RPC 的 /tasks/send 发起调用。关键设计是 RemoteAgent.run() 的签名和本地 Agent 完全一致——调用方感知不到对方是本地对象还是网络另一端的服务，这是"MCP 让远程工具和本地函数无差别"的思想在 Agent 层的复刻。

这是全书唯一真正需要"网络服务"的地方，两个端点就是全部协议面：GET /.well-known/agent.json 应答服务发现，POST /tasks/send 接收任务并把 Agent 的输出包成 artifact 返回。Python 侧随便挑一个轻量 Web 框架就能落地；TypeScript 侧这里选 Hono——路由写法几乎和 FastAPI 一一对应，且能零改动跑在 Node、Bun、Cloudflare Workers 等任意运行时上。

a2a_server.py 
from fastapi import FastAPI, Request

app = FastAPI()

@app.get("/.well-known/agent.json")   # 服务发现：我是谁、我能做什么
def agent_card():
    return {"name": agent.name, "description": agent.description}

@app.post("/tasks/send")                # JSON-RPC：接收任务，返回结果
async def tasks_send(req: Request):
    body = await req.json()
    user_input = body["params"]["message"]["parts"][0]["text"]
    result = await agent.run(user_input)
    return {"result": {"artifacts": [{"parts": [{"type": "text", "text": str(result.output)}]}]}}
import { Hono } from "hono";

const app = new Hono();

app.get("/.well-known/agent.json", (c) =>      // 服务发现：我是谁、我能做什么
  c.json({ name: agent.name, description: agent.description })
);

app.post("/tasks/send", async (c) => {         // JSON-RPC：接收任务，返回结果
  const body = await c.req.json();
  const userInput = body.params.message.parts[0].text;
  const result = await agent.run(userInput);
  return c.json({
    result: { artifacts: [{ parts: [{ type: "text", text: String(result.output) }] }] },
  });
});

export default app;

对照书中 scratch_agents/a2a_server.py 里真实用的是 AgentExecutor 适配层（把 Agent 包成事件队列消费者），上面这段是把该适配层"摊平"成最直接的两个 HTTP 端点，方便对照协议本身；remote.py 里的 RemoteAgent 客户端就是照着这两个端点用 fetch/httpx 发请求的那一侧。

本章要带走的几句话
  1. 单 Agent 的三堵墙——工具过多、指令冲突、上下文污染——解法是专业分工 + 三种协作模式。
  2. Workflow 代码定流程（共享 context）；Agent-as-Tool 咨询后收回控制（隔离 context）；Transfer 移交控制权（context 一起带走）。
  3. Workflow 继承 Agent 是为了组合律：可嵌套、可被包装成工具、可当子 Agent。
  4. Transfer 的工程细节全是防错设计：名字唯一、enum 锁死目标名单、工具只设标志而移交在 run() 层执行。
  5. A2A 用 Agent Card + JSON-RPC 把协作扩展到跨网络，RemoteAgent.run() 与本地签名一致。
