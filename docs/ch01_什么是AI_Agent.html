Chapter 01概念篇 · 无代码

什么是 AI Agent

在写一行 Agent 代码之前，先把边界画清楚：Agent 和普通脚本、聊天机器人的区别到底在哪，什么任务真的需要一个 Agent。

1.1三个要素撑起"自主性"

本书对 LLM Agent 的定义很朴素：一个把部分控制流交给 LLM 的程序——由模型自己决定下一步做什么、什么时候停，而不是开发者在代码里用 if/for 写死。让这件事成立，需要三个结构性元素同时出现：

🧠 LLM（大脑）

理解当前处境，决定下一步该做什么。

🛠️ 工具（手脚）

把行动空间扩展到外部世界：搜索、执行代码、查数据库。

第三个要素是循环——它让"决策"重复发生，直到目标达成，因为没人能提前知道一个任务需要几步、需要哪些工具。

1.3什么任务才配得上一个 Agent

Agent 更贵、更慢、错误还会传播——先问两个问题，能省则省：

  1. 这个任务需要 LLM 吗？ 结构化数据、输入范围有限、规则可枚举 → 传统代码更快更便宜。
  2. 需要 LLM，但需要 Agent 吗？ 单次调用能不能搞定？看任务复杂度（步数能否提前预知）、任务价值（值不值得多花几倍成本和延迟）、出错代价（错了容不容易发现、后果多严重）。

书中反复使用的试金石问题是："如果 Kipchoge 能一直保持马拉松世界纪录配速，跑到月球要多久？"——查纪录、查月地距离、做换算，步骤数不固定，正是 Agent 的用武之地。全书用 GAIA 基准（Meta & Hugging Face，2023）系统化收集这类问题，因为它答案明确、可以快速反馈，又不需要专业领域知识，很适合练习"观察失败 → 分析原因 → 改进"这个 Agent 开发的核心循环。

1.4上下文工程：决定 Agent 成败的隐藏变量

Agent 失败通常只有两种原因：模型不够聪明，或者该给的信息没进上下文。现实中后者占了大头——公司请假政策文档没被检索到，模型再强也答不出请假规则。这就是上下文工程（context engineering）存在的理由：不是简单地写好提示词，而是系统性地设计"工具结果怎么处理、保留多少对话历史、什么时候检索外部知识"。也别迷信"上下文越大越好"——研究显示更长的输入反而会让模型性能下降（"lost in the middle"），所以目标是精挑细选而不是塞满。

本书把上下文工程拆成五种策略，后面每一章基本都能对应上一种：

策略做什么对应章节
Generate 生成让 LLM 自己产出计划 / 反思，主动构建上下文第 7 章 规划与反思
Retrieve 检索从外部取信息塞进上下文：搜索、数据库、向量库第 3、5、6 章
Write 写入把上下文里的信息落盘：长期记忆、草稿、文件第 6、8 章
Reduce 压缩总结旧对话、删除冗余、按重要性过滤第 6 章
Isolate 隔离把任务/工具分进独立环境：沙箱、专用子 Agent第 8、9 章

再往外一层是harness engineering——当 Agent 真正跑在用户机器上、被真实产品使用时，模型之外的一切（记忆、安全执行、多 Agent 协作、用户的文件系统）都变得同等重要。书里的公式很直白：Agent = Model + Harness。这本书接下来的每一章，都是在往这个 Harness 里添砖加瓦。

本章要带走的几句话
  1. Agent = LLM（大脑）+ 工具（手脚）+ 循环（让决策重复发生直到完成）。
  2. Workflow 和 Agent 的分界线是"谁决定下一步"：开发者代码 vs. 模型实时判断，两者可以混用。
  3. 先问"需要 LLM 吗"，再问"需要 Agent 吗"——复杂度、价值、出错代价决定要不要上 Agent。
  4. Agent 失败的大头是"信息没喂对"而非"模型不够聪明"；上下文越大不等于越好。
  5. Agent = Model + Harness，本书后续每一章都在给这个 Harness 添加一种能力。
