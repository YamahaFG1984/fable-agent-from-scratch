构建 ReAct Agent

这一章把第 3 章那个 20 行的 while True 重构成一个真正的框架——全书后面 6 章都只是往这个骨架上挂功能，骨架本身不再变。

4.1ReAct = Reasoning + Acting

Agent 的本质是一个循环：思考（LLM 决定下一步）→ 行动（执行工具）→ 观察（结果进入历史）→ 再思考 → … → 最终回答。原始 ReAct 论文（2022）靠提示词让模型输出 Thought:/Action: 文本再用正则解析；现代做法直接用第 3 章学的原生 tool calling，模型输出结构化的 tool_calls，解析问题就此消失。

4.2四个组件，职责分离

组件职责一句话
ExecutionContext状态存储发生过的一切
BaseTool / FunctionTool能力抽象Agent 能做什么
LlmClient通信层和模型怎么说话
Agent编排循环本身

核心设计思想：context.events 是唯一事实来源（single source of truth）；每次调 LLM 前，都从 events 现做一个 LlmRequest 视图发出去。存储和呈现分离——这一刀切下去，第 6 章的上下文压缩才有了施展空间：改视图，不动历史。

4.3厂商中立的内部语言

types.py
class Message(BaseModel):      # 文本消息
    role: Literal["system", "user", "assistant"]
    content: str

class ToolCall(BaseModel):     # LLM 的调用请求
    tool_call_id: str
    name: str
    arguments: dict

class ToolResult(BaseModel):   # 执行结果
    tool_call_id: str
    status: Literal["success", "error"]  # ← 错误是一等公民
    content: list

整个框架内部只说这套厂商中立的语言，OpenAI/Anthropic 各自的原始格式被隔离在 LlmClient 的翻译边界上。错误处理哲学贯穿全书：工具异常、未知工具名、LLM 报错，全部变成历史里的一条 error 记录——让模型看见错误并自我修正，而不是让程序崩溃。

4.4结构化输出：把"最终答案"也做成工具

需求：让 Agent 返回 Pydantic 对象而不是散文，但中间步骤又要能自由调用工具。本章最聪明的技巧：自动注入一个 final_answer 工具，配合 tool_choice="required" 堵死自由文本出口——模型唯一的结束方式就是调用它。工具调用机制被复用成了输出约束机制，schema 校验和参数解析全都白送。

本章要带走的几句话
  1. ReAct = 思考→行动→观察的循环；现代实现用原生 tool calling，不再解析文本。
  2. 架构的灵魂是存储与呈现分离：events 是唯一事实来源，LlmRequest 是每次现做的视图。
  3. Message/ToolCall/ToolResult 是厂商中立的内部语言，各家 API 格式被压缩在通信层的翻译边界上。
  4. 错误处理：工具异常、未知工具名、LLM 报错全部变成历史里的 error 记录，让模型自我修正。
  5. 结构化输出 = "final_answer 也是工具" + tool_choice="required"——新需求不加新机制的典范。
