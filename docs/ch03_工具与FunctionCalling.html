Chapter 03scratch_agents/tools/

让 LLM 行动起来：工具调用

初学者最大的误解是"模型会调用工具"。真相是：模型只输出一段 JSON 声明"我想调用什么"，执行、安全、错误处理全都在你的代码里。

3.1工具调用的真相：一场结构化问答游戏

工具由两半组成：给模型看的一半是 JSON Schema 格式的工具定义（name / description / parameters），模型靠 description 决定何时用它；给 Python 跑的一半是普通函数，两者靠 name 关联，模型永远碰不到代码本身。

3.2工具设计准则：描述就是提示词工程

  • 模糊 vs 明确 —— book("Book something") 模型没法用；把参数格式（如 ISO-8601 日期）、取值范围写清楚才可靠。
  • 互相冲突的参数 —— 两个独立布尔值 on/off 可能同时为真；改成一个 enum，非法状态在 schema 层面就不存在。
  • 永远别让模型编造标识符 —— 要求模型提供 order_id 这种系统性数据，它会"编"一个像样的 ID 出来。正确做法：ID 由代码从上下文注入，模型只填它能从对话中真实获得的信息。

工具出错时也不该抛异常，而应该返回一句错误文本——异常会炸掉整个循环，错误文本却能进入历史，让模型看到后自我调整重试。

3.3用内省自动生成工具定义

手写 JSON Schema 太啰嗦。Python 的 inspect 模块能从一个普通函数里反射出全部信息：函数名 → name，docstring → description，类型注解 → 参数类型，有没有默认值 → 是否必填。这段逻辑（scratch_agents/tools/helpers.py）是第 4 章 @tool 装饰器的底层原理——从此"把函数注解和文档写好"从代码规范变成了直接影响模型行为的提示词工程。

3.4MCP：工具的标准化协议

MCP（Model Context Protocol）把工具做成独立的"服务器"进程，任何 Agent 即插即用——相当于工具界的 USB 接口。客户端走三步协议：initialize（握手）→ list_tools（发现）→ call_tool（调用）；服务端用 FastMCP 一个装饰器就能把普通函数注册成 MCP 工具，其自动生成定义的原理和第 3 节的内省完全一致。

本章要带走的几句话
  1. LLM 永远不执行工具——它只输出"调用意图"，执行权在你的代码里。
  2. 闭环四步：发清单 → 收 tool_calls → 执行并按 tool_call_id 回填 → 拿最终答案。
  3. 工具描述是提示词工程：具体、用 enum 消灭非法状态、永远别让模型造 ID；出错返回文本而非抛异常。
  4. inspect 内省把函数签名变成工具定义，是 @tool 装饰器和 FastMCP 的底层原理。
  5. 一个 20 行的 while True 循环就是 Agent 的雏形——第 4 章要做的只是给它加结构、安全和扩展性。
